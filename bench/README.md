# Benchmarks

Does editing through Vim commands (neovain) beat an agent's own editing tool? This harness
measures it with real, headless sessions in Claude Code and Codex CLI.

<!-- generated:summary -->
558 runs in 17 batches. 8 runs broke the rules and are left out of the tables.
<!-- /generated:summary -->

The tables in this file are generated from [`results.jsonl`](results.jsonl) by
`export_site.py`, which also builds the tables on [neovain.dev](https://neovain.dev).

## Method

Each run is a fresh agent session in its own directory, holding a copy of the task's fixture as
`work.py` and the task description as `TASKS.md`. The agent may change the file only one way.
A checker then scores the result.

**Tasks**

| Task | File | Changes |
|---|---|---|
| [`small`](tasks/small) | 70 lines | Seven small edits: a rename across every use, a new parameter, deleting a function, introducing a constant, wrapping a function body in try/except, deleting debug lines, swapping two functions. |
| [`large`](tasks/large) | 2,350 lines, generated by [`gen.py`](tasks/large/gen.py) | Six structural changes: delete a 398-line class, move a 401-line class to the end, swap two 300+ line classes, wrap a 122-line method body in `with self._lock:`, rename a method used 191 times, delete three `debug_` functions. |
| [`multi`](tasks/multi) | 13 files, 1,939 lines, generated by [`gen.py`](tasks/multi/gen.py) | Five API changes across a package: rename a function (114 sites, next to two look-alike names that stay), rename another and turn its second argument into a keyword (124 sites, 34 spanning lines), drop a keyword argument from every call (41, some with nested commas), replace `datetime.utcnow()` and extend the import in each file that uses it, delete a debug helper with its imports and calls. |

**Arms**

| Arm | How the agent may change the file |
|---|---|
| `edit` | Its own editing tool only. In Claude Code that is the Edit tool (exact string replacement). In Codex it is the built-in patch tool. |
| `neovain` | The neovain CLI only, through the shell. The agent is told to read the project README first. |
| `neovain-ex` | neovain with `NEOVAIN_EX_ONLY=1`: anchors and ex commands, no normal-mode keys. First round only. |
| `nvim` | Neovim itself, headless, as it comes: `nvim --clean --headless -n FILE -c ... -c wq`. The agent reads [`guides/nvim.md`](guides/nvim.md) instead of the README. |
| `ast-grep` | The [ast-grep](https://ast-grep.github.io) CLI only, which finds code by its syntax tree and rewrites every match. The agent reads [`guides/ast-grep.md`](guides/ast-grep.md). |

**Two scores.** The checkers compare the result with the expected file line by line, so one
extra blank line fails a run. Most failed neovain runs turned out to be exactly that, so every
run gets two scores:

- **Exact**: the file matches the expected one, blank lines included.
- **Code correct**: the code matches and only blank lines differ.

**Rules and how they are checked.** Claude Code's tools are switched on and off with
`--allowedTools` and `--disallowedTools`. Codex has no such switch, so its rules are set in the
prompt. After every run, `scan_violations` in [`run.py`](run.py) reads the run log for edits made
the wrong way: the editing tool in a neovain arm, neovain in the edit arm, or a shell command
that writes the file. A run with a violation is marked invalid and left out of every table. The
first version of this check knew only `sed -i`, redirects and `open(..., "w")`. It missed a model
that rewrote the file with `Path.write_text`, which came to light because that run's edit count
was zero. Since the `nvim` and `ast-grep` arms, the check looks past an arm's own tool calls (a
whole file carried inside an ast-grep template is not a shell write), and reading the
benchmark's own files, where the expected results are, counts as a violation too.

**Reasoning effort.** The first batches set no level, so each CLI chose. Claude Code uses
medium for Opus 5.5 and Sonnet 5.5, according to its documentation. Codex differs per model:
GPT-5.6 Sol defaults to low, Terra and Luna to medium. Later batches set `--effort medium`, and
every row records the level and whether it was set.

**neovain versions.** The neovain arm reads the "Using it well" section of the project README.
The tool and that section changed during the benchmarks, each time after looking at failures:

| Version | What changed |
|---|---|
| 0.1.0, guidance v1 | Anchor by content, prefer ex commands, read the diff. |
| 0.1.0, guidance v2 | Adds: plan the whole change and send it as one call, take blank lines along when moving a block ("mind the seams"), preview with `--dry-run`, quote steps in single quotes. |
| 0.1.0, guidance v3 | Replaces "mind the seams" with a method: a block owns the blank lines above it, so select both (`:-2,/^\S/-3`). Adds how to check and repair spacing. |
| 0.2.0 | The tool itself changed. After a large change it prints a summary of at most 80 lines in place of the diff: the blocks moved, deleted, inserted and re-indented, and `WARNING` lines about spacing and about ranges that ran too far. The guidance says how to read it (`v4` in `results.jsonl`). |

Guidance v3 and the summary were written after seeing that blank lines were the most common
failure, so they target what the checker punishes. Both are general help for any file with a
spacing convention, but their results should be read with that in mind. The edit arm gets no
matching help: it never reads the README, and the layout rule is in the task description for
both arms.

**A batch we threw away.** The first README for 0.2.0 explained the summary with a worked
example, and the example was the large task: its commands and the line ranges to expect. Every
run in the first 0.2.0 batch read it. Its large-task runs are left out (`tasks` in
`batches.json`). The example now uses an unrelated file, and the large task ran again with that
README. The small-task results are from the first batch, since the example gave nothing away
about the small task.

**The guides for the other tools.** neovain's arm reads the project README, whose advice went
through four rounds against these tasks. To compare tools and not advice, the `nvim` arm's guide
carries the same editing advice, rewritten for raw Neovim, plus what headless Neovim does that
neovain does not: it runs on after an error and exits 0, it keeps running when nothing quits, it
takes at most ten `-c` commands, and it prints nothing about what changed. The `ast-grep` guide
says how patterns, rules and `-U` work, that a preview costs nothing, and what a rewrite does to
layout. Every statement in both guides was checked against the tool. Neither guide mentions the
tasks. Both are first drafts, where neovain's is a fourth.

**Measures.** Token counts, cost and model time come from each CLI's own report. Output tokens
include thinking. API requests counts distinct model responses, which is the number of round
trips; it is not the same as tool calls, because models issue several tool calls from one
response. A shell loop that runs a tool on every file is one tool call. Codex reports neither
cost nor requests.

**Running it**

```
python3 run.py --task small,large --models opus,sonnet --arms edit,neovain --effort medium --reps 3
python3 run.py --agent codex --task small,large --models gpt-6-sol --arms edit,neovain --effort medium --reps 3
python3 run.py --task small,large,multi --models opus,sonnet --arms nvim,ast-grep --effort medium --reps 3
python3 collect.py          # batches.json -> results.jsonl, re-scoring every run from its log
python3 export_site.py      # results.jsonl -> the tables here and on the site
```

`batches.json` lists every batch with its agent and guidance version. The run logs themselves
stay on the machine that ran them.

On the large task neovain 0.2.0 is ahead. Over the six models with valid runs in both arms it

### Raw Neovim and ast-grep

Two questions the first rounds could not answer: how much of neovain's saving is Vim, and how
much is the wrapper around it; and whether a tool that understands syntax does better than one
that works on text. So two more arms, `nvim` and `ast-grep`, on every task, and a third task
built to suit ast-grep: `multi`, five API changes across a 13-file package. Claude Opus 5.5 and
Sonnet 5.5, and the seven Codex models, at medium effort, 3 runs per cell, neovain 0.2.0.

**Raw Neovim.** For Claude, Neovim without the wrapper came close. On the multi-file task it was
a little ahead (6 of 6 correct, 4,667 output tokens, against 5 of 6 and 5,122). On the large
task it was a run behind (5 of 6, 2,786 tokens, against 6 of 6 and 2,289). On small edits it
took twice the output and twice the time (2,651 tokens and 28s against 1,266 and 15s): its
second and third calls went to repairing what the first had left, an indent or a lost pair of
quotes. For Codex, neovain stayed ahead on the large task (16 of 21 correct against 12, 40%
fewer output tokens, half the time) and on the small one (36% fewer tokens, half the time, the
same scores), and the two were level on the multi-file task (10 of 21 each, 5,554 tokens against
5,531). Of the 9 Codex large runs that failed with raw Neovim, 5 changed code outside the
requested edits, which is what a command that keeps running after an error, then writes, looks
like.

**ast-grep.** The most expensive tool on every task, for both agents, and the least reliable,
including on the task built for it. A rewrite that deletes a node leaves its blank line and
its comma behind, so the models spent most of their calls on layout, and often gave up and
passed whole files through the tool: Claude in 11 of 16 valid runs, Codex in 20 of 63. That is
retyping, with extra steps. Opus was the exception on the multi-file task, 3 of 3 correct at
twice neovain's output; Sonnet went 0 of 3 there, and twice on the large task restored the
file from a backup with `cp`, which broke the rules and left those runs out.

**The multi-file task and the file that does not use `datetime.utcnow`.** One module imports
`datetime` for `fromisoformat` and never calls `utcnow`, so the task's fourth change does not
apply to it. 24 Codex runs, spread over all four tools, added `timezone` to that import anyway,
and failed on nothing else. That is a reading failure the tools share, and it hides the
differences between them. Counting those runs as correct, Codex's multi-file scores are:
neovain 19 of 21, Neovim 17 of 21, patch tool 14 of 18, ast-grep 14 of 21. The tables keep
the strict count.

**Wrong tool.** GPT-5.5, in all three of its large runs in the edit arm, rewrote the file with
Python scripts (`Path.write_text`), and in one of them piped a generated patch into
`apply_patch` from the shell. Those runs are invalid. In the pilot, Claude Haiku 4.5 gave up on
neovain in one of three runs and wrote the file with shell commands, eight times.

**Scripted patches.** In some large runs a Codex model wrote a Python script that computed the
new file and printed a patch, then applied the patch with its own tool. The file was changed
only by the tool, so these runs are valid. It is one reason the patch tool's token counts are
low.

**Wrong blank lines.** Almost all in Codex's neovain arm. Most often two extra blank lines at
the end of the file, left over after moving a class there together with the blank lines that
followed it.

**Throwing the output away.** neovain 0.1.0 printed the whole diff, about 2,000 lines on the
large task. Claude sent it to `/dev/null`, filtered it or kept only a few lines in 25 of its
30 large runs, and checked the result some other way. Codex did that in 4 of 60. Both of
Claude's wrong edits were in the `sync_all` wrap. In the one we examined, the line range ended
at the end of the class instead of the end of the method: valid Vim, wrong edit, and nobody
read the diff. With the summary of 0.2.0, Claude threw the output away in 1 of 6 large runs and
Codex in none of 21. The count covers the pipeline a neovain call is in: `> /dev/null`, a pipe
into `grep`, `wc`, `awk` or `sed`, or `head` or `tail` with fewer than 20 lines.

**Code in the wrong place.** Of Codex's five wrong large runs with 0.2.0, four changed code
outside the requested edits, mostly a class swap that landed in the wrong place. The summary
reported the move and named the first block it passed, which was not enough to show that it
had gone too far.

**Whole files through ast-grep.** A rule on `kind: module` whose fix is the entire file, or a
pattern of `$A` with the file as the rewrite: ast-grep as a way to write a file. Claude did it
in 11 of 16 valid ast-grep runs and Codex in 20 of 63, most often on the small task after the
first rewrites had left blank lines behind. Within the rules, and the same cost as retyping.

**Restoring from a backup.** Sonnet, twice on the large task with ast-grep, copied a saved
original back over `work.py` to start again. The copy is a shell write, so those runs are
invalid. GPT-5.5 rewrote files with Python scripts again, in all three of its multi-file runs
with the patch tool.

**One call per change.** Under guidance v1, Codex made a neovain call for each change, twelve
in one run. Claude chained its steps without being told.

**Doubled backslashes.** Codex wrote `\\<word\\>` on its first try at a rename, which matches
nothing. neovain refused the call and the next one was right.

## Findings

1. **Against Claude's Edit tool, neovain saves most on large structural edits** and ties on
   small ones. The saving is in output: the agent writes a range and a command, not the text.
2. **Against Codex's patch tool it depends on the edit.** That tool already avoids retyping.
   On small edits it needs well under half of neovain's output. On large structural edits
   neovain 0.2.0 needs about 40% less output and a third less time than the patch tool.
3. **Correctness depends on the model more than the tool.** Strong models pass with either.
   Weaker models fail the large task with either, in different ways: unfinished renames and
   damaged code with the patch tool, blank lines and misplaced blocks with neovain.
4. **Guidance has to say how, and it is not a cure.** Telling Codex to "mind the seams" changed
   nothing, so v3 gives a method for selecting blocks. With it, Codex's blank-line misses on the
   large task fell from 6 runs to 2 of 21, and exact scores rose from 12 to 14. Runs with wrong
   code went from 3 to 5, so code-correct scores fell from 18 to 16. At three runs per row that
   is a small net change. For Claude, v3 cut output on the large task.
5. **Agents do not read large diffs. They do read a summary.** With a 2,000-line diff, Claude
   threw the output away in 25 of 30 large runs; with the summary of 0.2.0, in 1 of 6. Codex's
   blank-line misses on the large task went from 2 of 21 runs to none, and its output fell by
   a quarter. Its runs with wrong code stayed at 5 of 21.
6. **Most of the saving is Vim; the wrapper matters more the more a model errs.** Raw Neovim
   with the same advice came close to neovain for Claude, and fell behind for Codex on the
   large and small tasks, where its runs failed in the way an editor that runs on after an
   error fails.
7. **Syntax awareness did not pay.** ast-grep was the most expensive and least reliable tool
   on every task, including the multi-file change built for it, because a rewrite that
   deletes a node leaves its line and comma behind, and the models then retyped whole files
   through it.

## Limitations

- Three runs per row. That shows large effects and not small ones, and pass counts on hard
  tasks vary from run to run.
- Two task sets, both Python, both single-file.
- Guidance v2 and v3 and the summary of 0.2.0 were written after seeing failures on these
  tasks.
- 0.2.0 changed the tool's output and the guidance together, so their effects cannot be told
  apart. Its batches ran on a later day than the edit arm they are compared with.
- The multi-file task has one file where a change does not apply. 24 Codex runs failed on that
  alone, so its strict scores say more about reading than about tools.
- The guides for Neovim and ast-grep are first drafts; neovain's advice had four rounds against
  these tasks.
- Codex's rules rest on the prompt and a log check, not on a switch.
- The models have been trained heavily on their own editing tools and not at all on neovain.
